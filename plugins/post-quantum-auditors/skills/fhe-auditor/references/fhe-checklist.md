# fhe-auditor Checklist

## Scheme identification and parameter security

- [ ] Scheme family, library version, and every parameter are read from
      code or the serialized context: ring degree, modulus chain, special
      primes, plaintext modulus or scale, secret and error distributions.
- [ ] The security estimate uses the actual secret distribution and the
      largest modulus key material is published under (special primes
      included); TFHE-style sets meet it for the LWE and GLWE instances.
- [ ] The library's parameter-security enforcement is on, and a peer
      cannot supply or negotiate a weaker context.

## Ciphertext modulus transitions

- [ ] Modulus transitions are explicit and validated at each transform:
      every switch, rescale, and level drop checks the operand's level.
- [ ] Modulus switching preserves the documented correctness and error
      bounds; its rounding error and CKKS scale drift are accounted for.
- [ ] Transition order is consistent across encrypt, evaluate, and decrypt
      flows: operands share a level and, for CKKS, a scale, or are rejected.

## Noise growth and budget

- [ ] Noise growth is tracked per operation, rotations and key switches
      included, and compared with the decryption bound.
- [ ] The claimed evaluation depth fits the measured or derived budget on
      the deepest path with worst-case plaintexts.
- [ ] The analysis states whether its bounds are worst-case or heuristic
      and the resulting failure probability, bootstrapping included.
- [ ] Overflow and exhaustion handling is deterministic and visible: an
      operation beyond the tracked level or noise estimate is refused.
- [ ] Plaintext range is enforced: no silent wrap modulo the plaintext
      modulus (BFV/BGV) or beyond the current level and scale (CKKS).

## Key switching and evaluation keys

- [ ] Products are relinearized before any operation that assumes a
      two-component ciphertext.
- [ ] Key-switch application validates dimensions and modulus
      compatibility, including decomposition base and digit count.
- [ ] Mismatched key-switch parameters fail closed; a missing rotation key
      is an error, not a fallback to another key.
- [ ] Key-switch keys are sourced and versioned from trusted material:
      generated by the key holder, bound to a key identifier and parameter
      set, authenticated in transit and at rest.
- [ ] No key-switching key targets another party's secret key unless
      re-encryption to that party is the design.

## Bootstrapping correctness

- [ ] Bootstrapping parameters match the intended scheme profile and fall
      inside the security estimate.
- [ ] Refresh steps preserve required secret-dependent terms: the key
      covers every secret coefficient and no correction step is dropped.
- [ ] Input preconditions hold at each call: message inside the padding or
      lookup-table domain (TFHE), inside the approximation range (CKKS).
- [ ] Bootstrapping failure paths avoid silent downgrade or stale
      ciphertext use.

## Decryption exposure

- [ ] Every sink of a decrypted value or a success/failure signal is
      listed with its observer.
- [ ] CKKS results leaving the key holder pass through noise flooding
      sized from a worst-case noise bound the key holder computes for the
      actual circuit.
- [ ] Exact schemes with observable results have a failure probability
      negligible against the decryptions an adversary can obtain.
- [ ] The decryptor does not reveal the result, an error class, or timing
      for ciphertexts of unverified origin.

## Plaintext leakage and slot packing

- [ ] Slot packing and unpacking enforce the expected isolation: slots a
      recipient must not see are masked before release.
- [ ] Plaintext debug and log paths do not leak ciphertext-derived
      secrets, plaintext operands, keys, or noise measurements.
- [ ] Plaintext/ciphertext boundary checks are explicit at every
      interface; no transparent or trivial (key-independent) ciphertext
      reaches a party that must not learn its content.
- [ ] Where the circuit or the evaluator's inputs are confidential,
      results are sanitized before returning to the key holder.

## Threshold decryption and untrusted inputs

- [ ] Partial decryptions add smudging noise that is never reused across
      ciphertexts, with a width justified for the permitted query count.
- [ ] A share is produced only for, and bound to, a ciphertext the parties
      agreed to decrypt; shares are validated if parties may be malicious.
- [ ] Deserialized ciphertexts and keys are checked for context
      identifier, ring degree, component count, level, coefficient range,
      representation, and scale; sizes are bounded before allocation.
